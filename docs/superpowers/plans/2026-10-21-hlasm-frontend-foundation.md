# HLASM Frontend — Tracking and Foundation Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** File the HLASM mega-epic and its issue tree, then build the foundation through the first milestone: a standalone HLASM program compiled to unit files, linked, run on the VM, returning its R15, and matching z390.

**Architecture:** A new C++ tool in the che4z fork (`hlasm_ast_bridge`) emits the macro-expanded, USING-resolved statement stream as JSON at end of assembly. A new leaf package `hlasm_asg` parses it into Pydantic models. `interpreter/hlasm/` lays each CSECT out as a VM byte region, lowers each statement to IR (one function per assembly, one label per statement address), and dispatches computed branches through an address→label chain. `interpreter/project/hlasm_compile.py` writes `.ast.json` → `.unit.json` → `.linked.json` like COBOL.

**Tech Stack:** C++20, CMake/Ninja, gtest, nlohmann_json (fork); Python 3.13, Pydantic, pytest; z390 (oracle).

**Spec:** `docs/superpowers/specs/2026-10-21-hlasm-frontend-design.md`

**Scope of this plan:** tracking (Tasks 1–4) and foundation (Tasks 5–12) up to the start/stop milestone and its merge (Task 13). Each opcode unit, the system-services units, the linkage unit and wave 2 get their own short plan when they start.

## Global Constraints

- Work on branch `hlasm`; push after every commit. Merge into `main` with `--no-ff` at milestones, then merge `main` back into `hlasm`. Never recreate the branch.
- No new IR opcodes. A builtin only when irreducible or IR is too cumbersome; the commit message says which.
- `hlasm_asg` is a leaf: it never imports `interpreter`. Bridge JSON becomes Pydantic models via `model_validate_json` on arrival; no dict indexing past that line.
- Trust che4z for symbol values, lengths, attributes, location counters and USING resolution. Python computes only what che4z does not: DC/DS byte images, section placement in VM memory, and runtime effective addresses.
- Machine claims z17 (arch15). AMODE 31/64; AMODE 24 unsupported.
- Unmasked program interruption → abend `S0Cx` ending the run unit.
- z390 tests carry the `z390` marker, excluded from the default run like `nist`.
- Every new Python file starts `# pyright: standard`. Frozen dataclasses, no `Any`, no comments beyond a one-line module/class header, no `for` loops with mutation.
- `xfail` reasons cite the bead id: `reason="... — red-dragon-xxxx"`.
- Never name an external codebase under analysis in any tracked artifact.
- Full gate before every commit: `uv run python -m black .`, `uv run pyright` (no new errors in promoted files), `uv run python -m python_fp_lint check --config fp.json interpreter/ cobol_asg/ hlasm_asg/`, `uv run lint-imports`, `make test PYTEST_ARGS="-q"`.

## Review Focus

- A branch to an address that is not a statement in this assembly (wild `BR`) must abend `S0C1`, not raise a Python error or loop. Pinned in Task 10.
- A program whose `END` names no entry point enters at the first CSECT's first statement. Pinned in Task 10.
- A source with assembly errors (che4z diagnostics of severity E or worse) is refused at the parse stage with the diagnostics in the error, not lowered. Pinned in Tasks 5 and 6.
- A statement generated inside a macro expansion keeps its origin (macro name, depth) through to the IR span, so a runtime abend points at the source line of the macro call. Pinned in Task 6 (origin in the model); the IR span is asserted in Task 11's WTO test.
- Recompiling unchanged source with unchanged settings reuses every artifact; changing a SYSLIB directory invalidates them. Pinned in Task 10.

- Produces: `hlasm_ast_bridge <src> [--syslib dir]...` writes this JSON (format 1) to stdout, exit 0; exit 2 with diagnostics JSON on stderr when any diagnostic has severity E/S:

```json
{"format":1,
 "sections":[{"name":"HELLO","kind":"CSECT","length":24}],
 "symbols":[{"name":"FIELD","kind":"RELOC","section":"HELLO","offset":16,"value":null,
             "length":4,"type":"F","scale":0,"integer":31}],

 "diagnostics":[]}
```

  Operand kinds: `REG`, `MASK`, `IMM` (`value`), `RELOC_IMM` (`section`, `offset` of the target), `STORAGE` (`displacement`, `index`, `base`, `length` — after USING resolution and mnemonic transforms, via `checking::evaluate_operands` + `apply_transforms`; declare `evaluate_operands` in a header in the fork). DC/DS statements have empty `operands` and one `data` item per operand: `{"type":"F","extension":"","duplication":1,"length":4,"explicit_length":false,"scale":0,"exponent":0,"nominal":<nominal>}` where `<nominal>` is `{"kind":"STRING","value":"..."}` (C/X/B/P/Z/F/H/E/D/L text as written) or `{"kind":"ADDRESSES","values":[{"kind":"ABS","value":n}|{"kind":"RELOC","section":"S","offset":n}|{"kind":"EXTERNAL","name":"X"}]}` for A/Y/S/V. DS is `nominal: null`. Assembler statements other than DC/DS (USING, DROP, EQU, ORG, LTORG, CSECT, …) are **not** emitted; their effect is already in offsets and resolved operands.
- Approach: in `analyze()`, keep only `proc_kind == ORDINARY` resolved statements with opcode type MACH, MNEMO or DC/DS (for model statements use the `evaluated_model == true` call); copy label, operands (`clone()`), range, macro frame (`scope_stack().back().this_macro`, depth `scope_stack().size()-1`) and a `dependency_evaluation_context` from `ordinary_assembly_dependency_solver(ord_ctx, li).derive_current_dependency_evaluation_context()`. After `analyze()` returns, evaluate each recorded statement with a solver rebuilt from its context (for literals, `unique_id + 1` — see `mach_processor.cpp:56`) and serialise. `origin.file/line` for an expanded statement is the macro **call** site in the open-code file (from `processing_stack_details()`), not the definition file.
